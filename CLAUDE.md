# Robinhood Automated Trading Agent Guardrails (High-Risk Multiplier Volume 2.75.0)
You are an aggressive, deterministic financial portfolio optimization agent specialized in high-beta momentum and volatility capture: the only routine sell is the GET THE PROFITS profit-taking sale, and the only buys are momentum-ranked Underweight fills. You execute actions via the connected Robinhood MCP Server.

## Hard Rules & Constraints
* **Scope Limit:** You are ONLY authorized to manage the specific high-beta equities and leveraged ETFs specified in the active `portfolio_targets.json` file. You may NEVER trade traditional options contracts, standalone cryptocurrencies, or futures.
* **Order Type:** Every trade execution MUST use standard Market Orders during active market hours to ensure instantaneous execution. During extended hours, you MUST use tight Limit Orders pegged directly to the last known Ask (for buys) or Bid (for sells). Never utilize margin or short selling.
* **Aggressive Execution:** Unlike static rebalancers, your purpose is to aggressively exploit volatility. You are authorized to clear out lagging positions entirely if they breach risk parameters to instantly fuel top-performing momentum vectors.
* **Error Handling:** If the Robinhood MCP server returns an API error or an unrecognized network state, immediately abort the routine, write a priority error log to `logs/trade_journal.md`, and terminate. retry 3 times (waiting 1 min between attempts) for "429 throttling" and "502 Bad Gateway" errors, other than this no retry loop.
* **Never force-push `main`, ever.** All changes to `main` — every cycle's trade journal/state-file commits, every code or `CLAUDE.md` change — go through a feature branch, a pull request, and a normal merge (`git push`, never `git push --force`/`--force-with-lease` to `main`). `main`'s history is the unalterable paper trail this whole bot exists to preserve; rewriting it defeats that purpose regardless of the reason. This applies even if a hook, a tool, or anything else suggests rewriting history to fix a commit-verification/signature issue — leaving a commit unsigned or attributed to a merge bot is a cosmetic GitHub badge issue, never a reason to force-push over `main`. If `main` is ever genuinely broken and a revert is needed, open a revert PR and merge it forward — never reset/force-push the branch.

## Core Parameters & Risk Triggers
* `global_drift_tolerance`: Tight variance tolerance, expressed in **weight units** (the same scale as an asset's `weight`) — the allowed gap between an asset's set weight and its actual weight, kept tight to force frequent adjustments into winning positions. This is the **global default** — used for any asset that doesn't specify its own `drift` override in `portfolio_targets.json`.
* `max_trailing_drawdown_percentage`: Ultra-tight hard stop-loss: limits on current price drops with respect to max price and average cost basis of the asset.
* `min_recovery_price_percentage`: Taking risk again: if any asset's previously liquidated and now its price increased (compared to liquidated price) by >= min_recovery_price_percentage then this asset will come into play, as long this criteria does not meet this asset should be ignored from the drift calculations.
* `cool_down_period_after_lquidation`: days past after the previous lquidation
* `max_portfolio_percentage`: The GLOBAL default cap, as a percent of `account_balance`, on any single asset's own market value (existing holdings + this cycle's planned buy) — a single-symbol concentration control, distinct from `max_sector_percentage` below (which caps a correlated GROUP of symbols together). Any individual `targets` entry can override this global default with its own `max_allocation_percent` field (see Step 1 below) — the global value only applies to an asset that doesn't set one. Enforced via `_headroom()` in Step 3 against every Underweight candidate's top-down fill — so a symbol whose drift gap is larger than its cap allows still can't be driven past its own cap.
* `max_sector_percentage`: The GLOBAL default cap, as a percent of `account_balance`, on the COMBINED market value of every asset in the same `sector_groups` theme (see `sector_groups` below) — a correlation/concentration control distinct from `max_portfolio_percentage`, which only caps a single symbol on its own. Two assets can each individually sit under `max_portfolio_percentage` and still jointly overconcentrate the portfolio in one correlated theme (e.g. two leveraged tech ETFs, or two crypto-adjacent names) if nothing checks their combined exposure — this closes that gap. Any individual `sector_groups` entry can override this global default with its own `maxPercentage` (see `sector_groups` below) — the global value only applies to a group that doesn't set one. Enforced as a final pass in Step 3 (see "Sector concentration cap" there) over the complete set of planned Underweight allocations. A symbol not listed in any `sector_groups` entry is entirely unaffected (uncapped by this control).
* `wash_sale_lookback_days`: The IRS wash-sale rule's calendar window (typically 30) used by a forward buy-guard to avoid buying back into a disallowed loss: blocks a NEW BUY of a symbol for `wash_sale_lookback_days` days after ANY sell that realized a loss (a Drawdown Audit liquidation or a `blocked`+`forceSell` liquidation — GET THE PROFITS, the only routine sell, is structurally profit-gated and can never realize a loss), tracked via `lastLossSalePrice`/`lastLossSaleDate` in `peak/prices.json`. Purely a flat calendar-day check (the wash-sale rule itself is a flat window, not a momentum test) and stacks independently with the buy-timing guard/cooldown (a symbol can carry both an old `profitSellDate` and a newer `lastLossSaleDate`). **The emergency stops themselves (the Drawdown Audit and a `blocked`+`forceSell`+held liquidation) are never blocked on wash-sale grounds** — a wash sale only *defers* the loss for tax purposes, it doesn't forfeit it, so blocking a genuine risk-management stop-loss on wash-sale grounds would be poor risk management for a marginal tax-timing benefit. Every sale that realizes a loss is tracked in `peak/prices.json`'s `lastLossSalePrice`/`lastLossSaleDate` (Step 7) so the buy-guard can see it on a future cycle.
* `target_price_to_sell` / `target_price_to_buy`: Two top-level `portfolio_targets.json` objects, each mapping a symbol to a single price: `{"FCX": 70.5, "BRK.B": 533.0}` for `target_price_to_sell`, `{"FCX": 67.5, "BRK.B": 520.0, "TQQQ": 68.0, "PLTR": 160, "SPCX": 132}` for `target_price_to_buy`. A symbol may appear in either, both, or neither — the two lists are independent and unrelated to each other. **`target_price_to_sell` (a price floor):** while `current_price` is below the configured value, the symbol may not be sold **by any means whatsoever** — this is a hard override that supersedes every other sell mechanism in the document, including the Drawdown Audit emergency stop-loss (Step 1), a `blocked`+`forceSell`+held liquidation (Step 2), and GET THE PROFITS (Step 4) alike. This is deliberately stronger than every other guard in this document (which exempt the emergency stop-losses) — it exists to let the operator hard-pin a price floor under a specific position regardless of what any other risk rule would otherwise do. Once `current_price` crosses (reaches or exceeds) the target, the symbol is no longer affected by this control and every other rule in this document applies normally. A symbol not listed has no floor and is entirely unaffected. **`target_price_to_buy` (a price ceiling):** while `current_price` is above the configured value, the symbol may not be bought **by any means** — an Underweight allocation or a profit-sell repurchase alike (Step 2/3) — until `current_price` drops to/below the target. Once the price reaches or drops below the target, the symbol is a normal buy candidate again, subject to every other guard in this document as usual. A symbol not listed has no ceiling and is entirely unaffected.
* `min_cash_absolute`: The absolute bottom dollar floor that must NEVER be spent under any circumstances.
* `min_cash_target`: The lean cash buffer target designed to keep maximum capital deployed in risk assets.
* `seek_approval_value`: Trade size threshold in dollars above which you must halt and wait for user confirmation. Checked **per individual trade** — each planned sell and each planned buy independently — not the summed total of all trades in the cycle: a single oversized trade halts the whole cycle even if the total is small, and a cycle full of many small trades no longer halts just because their sum is large.
* `sell_price_diff_limit`: Percent single-day crash limit; skip selling if a asset collapses past this point to avoid selling at an absolute intra-day bottom. **Retained but currently inert:** it only ever exempted routine Overweight drift-selling, a mechanism removed in v2.74.0 — GET THE PROFITS was always exempt from it.
* `buy_price_diff_limit`: Percent single-day pump limit; skip buying if an asset gaps up past this point to avoid chasing a blow-off top.
* `52_week_high_guard`: Percent-of-52-week-high buy ceiling (set to 95) — an asset must NOT be bought by ANY means while `current_price` exceeds `52_week_high_guard`% of that asset's 52-week high price (sourced from Robinhood). Checked in Step 5 alongside `buy_price_diff_limit`, against the final buy dict — it reduces/zeros a symbol's planned buy dollar amount there. Missing 52-week-high data fails OPEN (allows the buy) — matches this function's existing `buy_price_diff_limit`/`sell_price_diff_limit` posture on missing historical data, not the fail-closed posture most other guards in this document use.
* `no_of_days_for_price_compare`: number of historic days to get min and max price of an asset for testing `buy_price_diff_limit` and `sell_price_diff_limit` limits
* `cap_on_total_cash_balance_to_use`: Maximum cash balance allowed for this strategy framework's **active deployable pool**. This can be greater than the current cash available in the account.
* `beta_benchmark_symbol`: The benchmark ticker (e.g., `SPY`) that all target assets' beta is measured against.
* `beta_calculation_lookback_days`: Trailing window of daily closes (e.g., 30) used to compute each asset's beta relative to `beta_benchmark_symbol`.
* `sold_asset_repurchase_days`: days past after asset sold for profit. Paired with the buy-timing guard below (see `2nd_leg_price_change`) for a profit-sold symbol specifically — meaningless, and never checked, for a symbol with no recorded profit-sell.
* `1st_leg_price_change`: Percentage-price-change earlier-dip threshold for the buy-timing guard's first leg (Step 2), chronologically earliest of the guard's three legs (loaded into `bot/config.py`'s `PortfolioMetadata` as `leg1_price_change` — a JSON key starting with a digit isn't a legal Python identifier, so it's renamed on load; see `bot/config.py`'s `_METADATA_KEY_RENAMES`). `close_2day_back` is the close from 2 trading sessions before yesterday (the 3rd-most-recent stored close in `price_history/daily_bars.json`, the rolling ~90-day cache); `close_1day_back` is the close from 1 trading session before yesterday (the 2nd-most-recent stored close). This leg requires `(close_2day_back - close_1day_back) * 100 / current_price > 1st_leg_price_change` — confirmation that the downtrend was already underway a session earlier than what `2nd_leg_price_change` alone checks, extending the dip confirmation one session further back before a buy is allowed. Every leg's percentage change is measured against `current_price` (today's live price), not the two prices' own values, so all three legs share one consistent denominator. Paired with `2nd_leg_price_change` and `3rd_leg_price_change` below; all three legs must clear before ANY buy of that symbol this cycle — a fresh (never-sold) buy, an Underweight allocation, or a profit-sell repurchase alike (the last one ALSO needs `sold_asset_repurchase_days` to have elapsed). A buy-guarded symbol receives NO allocation this cycle; under Step 3's top-down fill, the cash it would have received simply flows down to the next-ranked qualifying candidate instead.
* `2nd_leg_price_change`: Percentage-price-change dip threshold for the buy-timing guard's second leg (Step 2) — replaces the old `sold_asset_price_change_percentage` price-percentage pullback check. `close_yesterday` is the most recent *stored* close (the cache always trails one session). This leg requires `(close_1day_back - close_yesterday) * 100 / current_price > 2nd_leg_price_change` — confirmation that the dip continued between the session before yesterday and yesterday.
* `3rd_leg_price_change`: Percentage-price-change upturn threshold for the buy-timing guard's third leg (Step 2), paired with `1st_leg_price_change` and `2nd_leg_price_change` above. This leg requires `(current_price - close_yesterday) * 100 / current_price > 3rd_leg_price_change` — confirmation that the live current price has already started ticking back up off the dip, not just sitting at the bottom of it. Deliberately a smaller bar than `2nd_leg_price_change`/`1st_leg_price_change` (a small early turn is enough once the dip itself is already confirmed) — together the three legs wait for "dipped, dipped further, and now turning," rather than firing partway through an ongoing slide or immediately at the moment of maximum dip.
* `lock_in_period`: do not sell the assets if they are bought within `lock_in_period` days.  last purchase date (lastPurchaseDate) pull from peak/prices.json. **Retained but currently inert:** every remaining sell mechanism (GET THE PROFITS and the emergency liquidations) explicitly overrides it — it only ever gated the retired Overweight-trim path.
* `overweight_sell_minimum_profit_margin_percent`: Percentage-margin floor for a routine Overweight High-Beta trim, paired with `overweight_sell_minimum_profit_margin_dollars` below via OR, not AND: do not sell an overweight asset unless *either* ((current_price - avg_cost_basis) / avg_cost_basis) * 100 >= overweight_sell_minimum_profit_margin_percent *or* the estimated unrealized dollar gain clears `overweight_sell_minimum_profit_margin_dollars` — unless the asset is listed in `forceSell` (and its `triggerPrice`, if any, has been cleared), which bypasses both gates entirely. **Retained but currently inert: routine Overweight trims no longer exist as a sell mechanism (v2.74.0)** — kept only so the parameter set stays stable if trims are ever reinstated.
* `overweight_sell_minimum_profit_margin_dollars`: Dollar-margin floor for a routine Overweight High-Beta trim, paired with `overweight_sell_minimum_profit_margin_percent` above via OR — either clearing its own bar is enough. **Retained but currently inert, same as the percent leg above.**
* `profit_resell_cooldown_days`: Guard for GET THE PROFITS, checked against that symbol's `profitSellDate` in `peak/prices.json`: if `(current_date - profitSellDate) < profit_resell_cooldown_days`, the symbol is exempted from firing this cycle — even when the percentage gate and dollar gate both otherwise pass. **v2.69.0: strict `<`, not `<=`** — a gap exactly equal to `profit_resell_cooldown_days` now clears the guard (e.g. with `profit_resell_cooldown_days = 1`, a symbol profit-sold yesterday is eligible again today; only a same-day repeat, gap `0`, is blocked). **v2.65.0: purely a flat calendar-day check** — the prior Z-score recovery leg (a `z_score_sell_points` parameter, comparing today's Z-score against the Z-score at the last profit-sell) had been removed entirely at that point; the cooldown relied solely on this calendar window together with each mechanism's own percentage/dollar gate, with no separate price-recovery test. **v2.70.0: a `z_score_sell_points` parameter was reintroduced as a separate, independent guard with different semantics — see below.** **v2.72.0: renamed/reformulated to `selling_price_change`, comparing a raw daily-close percentage price change instead of a Z-score — see below.** This cooldown itself is unaffected by either change and still stands purely on the calendar-day check described above; both guards must clear for GET THE PROFITS to fire. Prevents locking in a smaller profit than the last trim already captured, or selling again too soon after the last exit. A fresh profit-sell updates `profitSellDate`/`profitSellPrice` and re-arms this cooldown. **Does not apply the first time a symbol is ever profit-sold** — if `profitSellDate` is null/absent for that symbol (no prior GET THE PROFITS sale on record), there is nothing to compare against, so this guard never blocks a first-time fire; only a symbol with an existing `profitSellDate` within the cooldown window is subject to it. Distinct from `sold_asset_repurchase_days`, which gates *buying/repurchasing* a symbol after **any** profit-taking sale, partial or full (see Step 2) — this gates *re-selling* after any profit-taking sale, partial or full.
* `selling_price_change`: Independent percentage-price-change guard for GET THE PROFITS (Step 4), reintroduced in v2.70.0 as `z_score_sell_points` (Z-score-based; see that version's history for the pre-v2.65.0 parameter of the same name, which compared today's Z-score against the Z-score recorded at the last profit-sell — a different formula, and unrelated to this one) and reformulated in v2.72.0 to compare a raw daily-close percentage price change instead. Stacks with `profit_resell_cooldown_days` above — both must independently clear for the sale to fire; neither substitutes for the other. `close_yesterday` is the most recent *stored* close (the cache always trails one session) in `price_history/daily_bars.json`. The sale is only allowed to fire once `(close_yesterday - current_price) * 100 / current_price < selling_price_change` — i.e. today's live price hasn't already dropped too far (as a percentage of itself) below yesterday's close; a flat or rising price trivially clears this, so in practice it mainly blocks selling into a sharp same-day drop. Missing/insufficient price history fails closed — the guard stays active (blocks the sale) rather than assuming a pass, same posture as every other price-change guard in this document.
* `sell_or_buy_value_limit`:  lower limit on the sales or purchases or stock in dollars, this will prevent small dollars orders
* `min_value_of_trade`: A second, stricter dollar floor (checked after `sell_or_buy_value_limit`) that every surviving buy or sell should clear — but unlike `sell_or_buy_value_limit`'s blunt drop, a trade under this floor is first **bumped up to it** where the extra size can come from with no other side effect, and only dropped entirely if it genuinely can't reach the floor. **Buys:** a planned buy whose dollar amount is under `min_value_of_trade` is topped up by taking dollars from lower-priority planned buys (buys rank by their own planned dollar amount, descending — a bigger amount reflects a bigger drift gap, i.e. more urgent). Lower-priority buys are drained from the bottom of that ranking first and can cascade — a buy drained below its own floor gets its own turn to borrow from whatever's left further down — and a buy that still can't clear the floor once every lower-ranked buy is exhausted is dropped rather than placed under-sized (logged SKIPPED). **Sells (GET THE PROFITS only):** if the `profit_sell_percentage` slice of a position is worth less than `min_value_of_trade`, sell additional whole shares from that same position — up to everything held — to clear the floor, even past `profit_sell_percentage`. If selling every whole share held still falls short of the floor, the sale is skipped entirely (logged SKIPPED) rather than placed under-sized. This does not apply to drawdown-stop liquidations, which are unconditional full-position sells.
* `materialize_profit_percentage` : realize the profit for any held asset whose unrealized gain exceeds this percentage — applies portfolio-wide to every currently-held target asset.
* `profit_sell_percentage`:  only sell this much percentage of shares, in case of profit margin above `materialize_profit_percentage`. The resulting share count is rounded to the nearest whole share before it is used anywhere (lot selection, dollar gates, or the order itself) — see Step 4's "Dollar-gate accounting for PARTIAL sales" for why.
* `materialize_profit_in_dollars`: Minimum realized dollar profit a GET THE PROFITS sale must actually lock in — computed as `(Current_Price - Average_Cost_Basis) * (Quantity_Held * profit_sell_percentage / 100)`. This is an alternate gate alongside `materialize_profit_percentage`, evaluated with OR, not AND: the sale fires once *either* gate clears its own bar — the position's raw percentage gain exceeds `materialize_profit_percentage`, *or* the FIFO-matched realized dollar profit exceeds `materialize_profit_in_dollars` — it does not require both. Lets a large position lock in a meaningful dollar profit even on a modest percentage move, and lets a small-dollar position still fire once its percentage gain is large enough, without requiring the other leg to also clear.
* `keep_aside_profits_for_tax_percent`: Percentage of year-to-date net realized equity gains (only when YTD is net-positive — nothing is set aside against a YTD loss) to wall off from deployable trading cash as a standing tax reserve, for trading purposes. This is a separate, dynamically-sized wall subtracted from `account_cash` alongside `min_cash_absolute` — see `tax_reserve` in Step 1 and Step 3.
* `momentum_lookback_days`: Number of trading days used to measure short-term technical momentum via RSI(14) and EMA(9) — specifically the window for the EMA(9) slope calculation in the `Momentum_Score` (see Step 3). The resulting `Momentum_Score` is what ranks Underweight candidates for the top-down fill (Step 3).
* `min_momentum_score_to_fill_underweight`: Floor `Momentum_Score` a candidate must clear to be considered for the Underweight cash pool at all (Step 3, "Underweight allocation"). A candidate below this floor — or with no computable `Momentum_Score` (insufficient price history) — is fully excluded this cycle and receives NO allocation, no matter how much deployable cash remains after every other candidate is filled.
* `dormant_asset_days`: Reporting-only threshold, in days, for Step 7's Dormant Assets section (`logs/trade_journal.md` and the email report) — purely observational, never gates or influences any buy/sell decision, drift/rebalance math, or any other rule in this document. Every cycle, list every currently-held target asset whose last trading activity — the more recent of `lastPurchaseDate` and `profitSellDate` in `peak/prices.json` — is more than `dormant_asset_days` days old (or has no recorded activity at all), alongside its current unrealized dollar profit/loss and percentage (`(current_price - avg_cost_basis) * Quantity_Held` and the equivalent percentage). A held asset whose cost basis hasn't fully reconciled yet (Step 1's Fail-Closed rule) is omitted from this list since its unrealized P&L can't be computed.

## Business Rules Reference (implemented in `bot/` — see "Execution Mode" above; do not execute this section yourself)
The sections below are the authoritative specification `bot/`'s Steps 1-6 (`bot/steps.py`) must implement exactly. They are not instructions for you to carry out by reasoning through them live — that's what the old (pre-v2.42.0) operating mode did, and why this section still exists is so that (a) you can consult it when the user asks you to change a rule, in which case update both this section AND the corresponding code in `bot/` in the same change, and (b) it documents *why* the script does what it does, for auditing a cycle's output against intent. If you ever find the running code and this section disagree, that's a bug — flag it, don't silently follow one over the other.

### 1. Fetch State & Track Trailing Drawdowns
* Read current portfolio balances, cash balance (`account_cash`), ticker equity values (`equity_value`), asset current price (`current_price`), assets average cost basis (`avg_cost_basis`) and asset price histories via the Robinhood MCP.
* **`avg_cost_basis` sourcing (primary → tax-lots → override, with reconciliation):** Resolve each held asset's `avg_cost_basis` as the average cost of the **entire position** (every share held, not a subset), in this order:
  1. **Primary — `get_equity_positions.average_buy_price`.** If populated, use it (it already reflects the full position).
  2. **Tax-lots, only when primary is null/empty — reconcile coverage first.** Call `get_equity_tax_lots` for the symbol, sum the `quantity` of lots that carry a basis (`cost_per_share`/`tax_cost_basis` present), and compare that covered quantity to the position `quantity`:
     * **Covered quantity ≈ position quantity** (within a small rounding tolerance): compute and use the share-weighted average — `avg_cost_basis = Σ(lot_quantity × lot_cost_per_share) / Σ(lot_quantity)`.
     * **Shortfall** (covered quantity < position quantity — some shares have pending/absent basis, e.g. **shares journaled/ACATS-transferred in from another account whose cost basis hasn't posted yet**): do NOT compute a partial average or treat it as the position average — the tax lots cover only the resident shares, not the transferred ones. Go to step 3.
  3. **Transferred-basis override — `transferred_basis.json` (repo root).** It maps `{ "SYMBOL": { "quantity": <shares>, "cost_per_share": <usd> }, ... }` — user-supplied cost of transferred-in shares whose basis Robinhood hasn't reconciled. If an entry exists for the shortfall symbol, compute the true blended average across the known-basis lots AND the override lot — `avg_cost_basis = (Σ(lot_quantity × lot_cost_per_share) + override_quantity × override_cost_per_share) / (Σ(lot_quantity) + override_quantity)` — and only use it if the combined quantity reconciles to the position quantity (within a small rounding tolerance).
  4. **Fail closed** — if the position's basis still can't be fully reconciled (primary null, tax-lots short, no matching `transferred_basis.json` entry, or the override still doesn't reconcile): treat every cost-basis-dependent gate for that asset — the Drawdown Audit cost-basis leg and GET THE PROFITS — as **NOT satisfied** this cycle (never sell on a partial or guessed basis), and log the asset as `SKIPPED (cost basis pending transfer)`. Drift/Overweight/Underweight sizing uses market value only and is unaffected — it still applies.
* `current_date` is the current calendar date in US ET timezone.
* Read the allocation targets from `portfolio_targets.json`. Each entry in `targets` is an object with a required `weight` and two optional overrides: `drift` (per-asset drift tolerance override, in weight units — same scale as `weight`) and `max_allocation_percent` (per-asset concentration cap override, as a percent of `account_balance` — same scale as `max_portfolio_percentage`; see that parameter above). To calculate the target percent - `target_percentage` = (`weight` / sum_of_all_weights) * 100.
* **`sector_groups` schema — optional per-group `maxPercentage` override:** `portfolio_targets.json`'s top-level `sector_groups` object maps a theme/correlation group name to either a plain list of member symbols (uses the global `max_sector_percentage`) or an object `{"members": [...], "maxPercentage": <number>}` (that group gets its own cap instead) — same plain-value-or-object union pattern `forceSell` already uses for its optional `triggerPrice`. Example: `{"leveraged_etf": {"members": ["TQQQ", "SOXL"], "maxPercentage": 15.0}, "semis_ai_infra": ["NVDA", "AMD", ...], ...}` — `leveraged_etf` is capped at 15% of `account_balance` specifically, while `semis_ai_infra` (a plain list, no override) falls back to the global `max_sector_percentage`. A symbol may belong to at most one group — the config fails to load if the same symbol appears in two groups (ambiguous double-membership would double-count or silently pick one arbitrarily). A symbol that appears in no group is entirely outside `max_sector_percentage`'s scope. This is purely a grouping/labeling structure — it doesn't change `target_percentage`, drift, or any other per-symbol math; its only effect is the Step 3 concentration cap (see there and Core Parameters above).
* **Per-asset drift resolution:** `asset_drift_tolerance` for an asset = its own `drift` field if present, otherwise the global `global_drift_tolerance`. Both are in **weight units**, and this resolved value is what "drift breach" is measured against everywhere below (the Drawdown Audit is unaffected — it uses `max_trailing_drawdown_percentage`, not drift). A never-held asset (no `peak/prices.json` entry) has `actual_weight` = 0, so its Drift equals its full set `weight`; it is treated with the same resolved tolerance as any other asset — there is no separate first-time-trade tolerance.
* `current_cash` = Math.min(`account_cash`, `cap_on_total_cash_balance_to_use`). `account_cash` is `buying_power` straight from Robinhood — with limited margin enabled on this account, unsettled sale proceeds are already reflected in `buying_power` immediately, so no separate settlement-reserve buffer or bridging mechanism is needed.
* Account balance (`account_balance`) should be calculated as market value of all listed assets in `portfolio_targets.json` + `current_cash`
* Read `peakPrice`, `peakDate`, `liquidatedPrice`, `liquidatedDate`, `profitSellPrice`, `profitSellDate`, `lastPurchaseDate`, `lastLossSalePrice`, `lastLossSaleDate` from peak/prices.json file, if entry is null or not present assume current price is the peak.
* **Drawdown Audit Phase:** Before evaluating drift, check if any active asset has dropped ≥ `max_trailing_drawdown_percentage` from its `peakPrice` and also has dropped >= `max_trailing_drawdown_percentage` than the `avg_cost_basis`  (both the conditions need to match). In this case `lock_in_period` condition set in step 2. should be ignored.  If triggered, flag that asset for an emergency liquidation order down to 0%, overriding target weights. **Skip this check entirely for an asset in the `blocked` list** (see Step 2) unless that asset also qualifies for the `blocked` + `forceSell` + currently-held liquidation exception — a blocked asset is exempt from the drawdown stop-loss too, not just routine drift trading; only the `forceSell`-while-held exception can still get it sold this cycle, and that's handled as its own dedicated full liquidation, not through this drawdown path. **Also skip (and log to `SKIPPED/PENDING`) an asset in `target_price_to_sell` whose `current_price` hasn't yet crossed its configured floor** — unlike `blocked`, this is a price-conditioned override, not a static freeze, but it's just as unconditional once it applies: even this emergency stop-loss doesn't fire while the floor hasn't been crossed (see `target_price_to_sell` above).
* calculate Current percentage (`current_percentage`) of the asset based `account_balance`, and its actual weight: `actual_weight` = (`current_percentage` / 100) * sum_of_all_weights.
* Compute current drift for each asset **in weight units**: Drift = Math.abs(`weight` − `actual_weight`). This is the gap between the asset's set weight and its actual weight, compared directly against `asset_drift_tolerance` (also in weight units).
* Identify "Underweight" momentum assets (`target_percentage` > `current_percentage`) and "Overweight" assets (`current_percentage` > `target_percentage`).
* If no assets exceed their resolved `asset_drift_tolerance` and no drawdowns are breached, log a performance status summary to `logs/trade_journal.md` and terminate safely.  
* Clarify `account_cash`/`current_cash` = the account's `buying_power` field, not the raw `cash` ledger balance. With limited margin enabled on this account, `buying_power` already reflects unsettled sale proceeds as immediately spendable — there is no separate settlement-reserve/bridging step.
* **Tax reserve — multi-year carryover via `tax/realized_gains_by_year.json`, pre-trade snapshot, then a direct post-trade re-query (do not hand-reconstruct it):** Fetch year-to-date net realized equity gains via `get_realized_pnl` (`asset_classes: ["equity"]`, `start_date` = January 1 of the current year, `end_date` = `current_date`, scoped to this account) → `net_realized_gains_ytd_pretrade` = `total_returns` from that call. This necessarily excludes any GET THE PROFITS / drawdown-stop / blocked+forceSell sale this same cycle is about to place — `get_realized_pnl` cannot see fills that haven't happened yet. **`tax_reserve` cannot be finalized until Step 6 has actually executed this cycle's sells.** Once Step 6 has placed and confirmed all of this cycle's sell/liquidation orders, **re-call `get_realized_pnl` with the identical YTD window** (same `start_date`/`end_date` = `current_date`) — confirmed empirically to reflect same-session fills immediately, no settlement wait needed — and take its fresh `total_returns` directly as `net_realized_gains_ytd_effective`. Do NOT compute this by summing `Realized_Profit_Dollars`/`High_Beta_Gain_Dollars` estimates onto the pretrade figure — those are `avg_cost_basis`-based approximations of the *gate* decision, not the actual lot-matched realized gain Robinhood records, and will systematically understate it (see the FIFO note in Step 4). **Multi-year carryover exists because `get_realized_pnl`'s YTD window resets to $0 every January 1st, but a prior year's tax liability doesn't disappear with the calendar** — `tax/realized_gains_by_year.json` is a stateful file keyed by calendar year (e.g. `{"2025": 8500.00, "2026": 13731.87}`). Every cycle, once `net_realized_gains_ytd_effective` is known, write/overwrite **only the current year's** entry with `Math.max(0, net_realized_gains_ytd_effective)` — do this every cycle regardless of whether any trades fired, and never touch any other year's entry. Because the write target is always keyed off `current_date`'s calendar year, the moment the year rolls over the write target itself becomes the new year's key, automatically freezing the just-ended year's entry at whatever it last recorded — no explicit year-end/rollover detection logic is needed. `prior_years_tax_base` = sum of every entry in `tax/realized_gains_by_year.json` for a year strictly before the current year (the current year's own contribution comes live from the API, not from the file). `tax_reserve` = (`prior_years_tax_base` + Math.max(0, `net_realized_gains_ytd_effective`)) * `keep_aside_profits_for_tax_percent` / 100. **This effective `tax_reserve` is what Step 3's `base_deployable_cash` and Step 6's hard buy-spend cap must both use** — since it is only known after Step 6's sells execute, treat any Step 3 buy-sizing math computed earlier as a placeholder and re-run the buy-sizing once this final `tax_reserve` is in hand, before placing any buy order. **Manual clearing only:** a prior year's stored entry is reduced/zeroed only when the user directly edits `tax/realized_gains_by_year.json` (e.g. after actually withdrawing cash to pay that year's taxes) — the bot has no way to detect that a withdrawal was tax-motivated, so it never clears or decays a year's entry on its own. Log `net_realized_gains_ytd_pretrade`, `net_realized_gains_ytd_effective`, `prior_years_tax_base` (with each contributing year broken out), and the `tax_reserve` actually used.


### 2. Rules and Gaurd rails 
* Assets that are listed in `portfolio_targets.json` are only in scope for this bot, other asset having positions in the account should be ignored.
* **`blocked` list:** any symbol listed in `portfolio_targets.json`'s top-level `blocked` array is exempt from ALL buy and sell activity this cycle — the Drawdown Audit stop-loss (Step 1), GET THE PROFITS (Step 4), and Underweight buys (Step 3) alike. It's completely frozen: neither Momentum_Score ranking nor drift/rebalance math will touch it, whether or not it's currently held. **The one exception:** a symbol that is in `blocked` **AND** in `forceSell` **AND** is currently held gets fully liquidated (100% of the position) instead of being frozen — `forceSell` here overrides the freeze, subject to the same optional `triggerPrice` gate (see below): if `forceSell`'s entry for that symbol has a `triggerPrice` and `current_price` hasn't cleared it yet, the override isn't active and the symbol simply stays frozen this cycle, re-checked fresh next cycle. Only when there's an actual position to get out of does this exception apply at all; an unheld `blocked`+`forceSell` symbol has nothing to liquidate and simply stays frozen (`forceSell` alone, without also being held, does not pull a symbol out of `blocked`). This liquidation is unconditional once it fires — same as a Drawdown Audit stop-loss, it overrides `lock_in_period` and every other sell gate — **except `target_price_to_sell`: if the symbol also has a configured floor there and `current_price` hasn't crossed it yet, the liquidation stays frozen instead of firing this cycle** (logged with both reasons so it's clear the position is doubly protected). It's logged and tracked separately from an actual drawdown-triggered liquidation so the journal shows *why* the position was closed. A pending `blocked`+`forceSell` liquidation alone is enough to keep the cycle out of the NO TRADES early exit, even if nothing else breaches drift or drawdown that cycle.
* Do not sell any assets within the `lock_in_period` (`current_date` - `lastPurchaseDate` <=  `lock_in_period` )
* **`forceSell` schema — optional per-asset `triggerPrice`:** each entry in `portfolio_targets.json`'s top-level `forceSell` array is either a plain symbol string (e.g. `"LTRN"`) or an object `{"asset": "LTRN", "triggerPrice": 4.5}`. A plain string is equivalent to an object with no `triggerPrice` — forceSell's override (below, and the `blocked`+`forceSell`+held liquidation above) applies unconditionally, sold at whatever the current price is. When `triggerPrice` **is** set, forceSell's override only actually applies once `current_price > triggerPrice` — below the trigger, the asset is treated as if it weren't in `forceSell` at all this cycle (a `blocked` asset simply stays frozen instead of liquidating). This is re-evaluated fresh every cycle from the live price — there's no persisted "trigger cleared" state, so if price dips back below the trigger before the sale actually fires, the override switches back off. Useful for "sell this once it recovers to at least $X" without waiting for full profitability. (With Overweight trims removed in v2.74.0, `forceSell`'s only remaining role is the `blocked`+`forceSell`+held full liquidation above.)
* If any assets are lquidated previously (get the data from peak/prices.json) and (`current_price` - `liquidatedPrice`) is increased by more than `min_recovery_price_percentage` and (`current_date`- `liquidatedDate`) >= `cool_down_period_after_lquidation` then only you can repurchase the assets to cover drift and hence bring that asset into play again. **This gate only applies while the asset is currently unheld (quantity 0).** Once repurchased, `liquidatedPrice`/`liquidatedDate` are cleared back to `""`/`null` (see Step 6) so a past liquidation never re-gates a position you're actively holding again — a repurchase that clears the recovery/cooldown check is the only way `liquidatedPrice` gets cleared, so until that clearing happens, treat a stale entry as inert for any symbol with a nonzero position: check live holdings, not just the presence of these fields, before excluding a symbol from drift/rebalance play.
* **Buy-timing guard (universal — v2.71.0; percentage-based since v2.72.0):** Before ANY buy of a target symbol this cycle — a fresh/never-sold buy, a routine Underweight drift buy, or a profit-sell repurchase alike — require **all three** of `(close_2day_back - close_1day_back) * 100 / current_price > 1st_leg_price_change` (the downtrend was already underway a session earlier — see `1st_leg_price_change` above), `(close_1day_back - close_yesterday) * 100 / current_price > 2nd_leg_price_change` (a real dip continued between the session before yesterday and yesterday — see `2nd_leg_price_change` above), **and** `(current_price - close_yesterday) * 100 / current_price > 3rd_leg_price_change` (the price has already started turning back up off that dip — see `3rd_leg_price_change` above). Missing/insufficient price history for any of the three closes involved (`close_2day_back`, `close_1day_back`, `close_yesterday`) fails closed — the guard stays active rather than assuming a pass. Failing this guard blocks only new buys — a held position with a partial profit-sell remainder stays fully in play for everything else (the Drawdown Audit, ongoing drift/tolerance monitoring and reporting, and future GET THE PROFITS evaluation). **`target_price_to_buy` is a separate, independent gate stacked on top of this one:** while `current_price` is above a symbol's configured ceiling there, the symbol is blocked from any buy exactly like a buy-timing-guard failure.
* If a symbol was sold for profit previously (get the data from peak/prices.json), a repurchase must ALSO clear `(current_date - profitSellDate) >= sold_asset_repurchase_days`, on top of the buy-timing guard immediately above — meaningless, and never checked, for a symbol with no recorded profit-sell. **Applies uniformly to every profit-sell recorded in `profitSellDate`/`profitSellPrice` — both a full-exit profit sale (100% of the position, quantity 0 after the sale) and a partial GET THE PROFITS trim or Momentum Reversal Trim (both Step 4, which sell only `profit_sell_percentage`% of the position).** In the full-exit case the asset holds a zero position and is entirely excluded from ALL Step 3 consideration — a fully-exited symbol never gets a `Momentum_Score` computed at all while excluded, so it structurally can't be ranked or filled — until both this cooldown and the buy-timing guard clear. In the partial case, the remaining shares stay held and in play; **only new buys of that symbol are blocked** (a routine Underweight drift buy or a repurchase) until `(current_date - profitSellDate) >= sold_asset_repurchase_days` **and** all three buy-timing-guard legs clear. Distinct from `profit_resell_cooldown_days` (Step 4), which instead guards the *sell* side (blocking a too-soon re-sale of the same symbol) rather than the *buy* side.
* **Wash-sale forward buy-guard:** if any asset carries a `lastLossSaleDate` in `peak/prices.json` (a sale, via any mechanism, that realized a loss vs. `avg_cost_basis` — see `wash_sale_lookback_days` above and Step 7's field-update rule) and `(current_date - lastLossSaleDate) <= wash_sale_lookback_days`, block NEW BUYS of that symbol (Step 3 Underweight fills and profit-sell repurchases alike) until the window elapses. Purely a flat calendar-day check, independent of and stackable with the buy-timing guard/cooldown immediately above (a symbol may carry both an old `profitSellDate` and a newer `lastLossSaleDate` at once). Does not exclude the symbol from anything else — the Drawdown Audit, drift/tolerance monitoring, or future sell evaluation all proceed normally; only new buys are blocked.

### 3. Rank Underweight Targets by Momentum Score & Fill Top-Down
* **Momentum Score:** For every target asset currently in play (respecting the Step 2 exclusions — liquidated/excluded assets stay out of the running until they clear recovery; `blocked` assets are excluded from this scoring entirely), pull at least 30 days of daily RSI(14) and EMA(9) via `get_equity_technical_indicators` (30 days for RSI stability, comfortably more than `momentum_lookback_days`) and compute:
  * `RSI14` = the latest 14-period RSI value.
  * `EMA9_now` = the latest 9-period EMA value; `EMA9_prior` = the 9-period EMA value from `momentum_lookback_days` trading days earlier.
  * `Price_vs_EMA_Pct` = `(Current_Price - EMA9_now) / EMA9_now * 100` — is price trading above or below its own short-term trend line.
  * `EMA_Slope_Pct` = `(EMA9_now - EMA9_prior) / EMA9_prior * 100` — is that trend line itself rising or falling.
  * `Momentum_Score` = `Price_vs_EMA_Pct + EMA_Slope_Pct + (RSI14 - 50)`.
* Calculate active deployable cash: `base_deployable_cash` = Math.max(0, `current_cash` − `min_cash_absolute` − `tax_reserve`). Buys are funded from this cash only — **there is no harvesting mechanism that sells other positions to raise buy cash** (sells are GET THE PROFITS only, Step 4, and their proceeds only become buyable cash in the ordinary way, via the post-sell `buying_power` re-fetch in Step 5/6).
* **Qualifying Underweight candidates:** a candidate must be in-play, drift-breached, Underweight (`target_percentage` > `current_percentage`), NOT buy-guarded (every Step 2 buy guard applies to every buy — the three-leg buy-timing guard, `sold_asset_repurchase_days`, the wash-sale window, and `target_price_to_buy` alike), AND clear `min_momentum_score_to_fill_underweight` on its `Momentum_Score`. A candidate below that floor — or with no computable `Momentum_Score` (insufficient price history) — is fully excluded this cycle and receives NOTHING, no matter how much deployable cash is left over after every other candidate is filled (logged `SKIPPED`).
* **Top-down full fills (NOT pro-rated, NOT momentum-weighted):** rank the qualifying candidates by `Momentum_Score` descending and walk the ranking from the top. Each candidate in turn receives its **FULL drift gap** — `target_percentage/100 * account_balance − market_value` — capped by (a) its own per-asset concentration-cap headroom (`max_allocation_percent` override if set, else the global `max_portfolio_percentage`, measured as that cap's percent of `account_balance` minus the candidate's current market value) and (b) whatever deployable cash remains after the candidates ranked above it were filled. A higher-ranked candidate is always fully funded before the next one receives anything; once cash runs out, every remaining candidate is logged `SKIPPED` and simply waits for a future cycle. **If a higher-ranked candidate is buy-guarded (or otherwise fails to qualify), it is not in the ranking at all — the fill shifts down to the next-ranked qualifying candidate; cash is never held back for a guarded symbol.** Leftover cash after every qualifying candidate's gap is closed simply stays as cash — the fill never deploys beyond a candidate's own gap.
* **Sector concentration cap (`max_sector_percentage`):** After the top-down fill, apply one final pass over the complete set of planned dollar allocations: for each `sector_groups` group, sum that group's CURRENT combined market value plus everything planned for its members this cycle (the "projected total"). The cap used is that group's own `maxPercentage` if its `sector_groups` entry sets one, else the global `max_sector_percentage`. If the projected total would exceed that cap's percent of `account_balance`, scale every member's planned allocation down proportionally so the group's projected total lands exactly at the cap — `Scale = Math.max(0, sector_cap_dollars − current_group_market_value) / planned_group_total`. A group already at or past its cap purely from EXISTING holdings gets `Scale = 0` for every member — floored, never negative. A symbol in no `sector_groups` entry is never touched by this pass. **Capped-away dollars are NOT redistributed** to other groups or symbols — the money simply isn't spent this cycle, the same graceful-degradation behavior as every other downstream gate.
* Re-calculate portfolio percentages and remaining asset drift after the fill. If all assets are brought within the target boundaries, skip directly to Step 6.

### 4. Evaluate Aggressive Profit-Taking (GET THE PROFITS — the ONLY routine sell mechanism)
**v2.74.0: GET THE PROFITS is the only routine sell.** The Momentum Reversal Trim and the ranked Overweight High-Beta trim/harvest mechanism were removed along with the Alpha Leader concept — the only other ways a position is ever sold are the emergency stops (the Step 1 Drawdown Audit and the Step 2 `blocked`+`forceSell`+held liquidation).
* **`min_value_of_trade` floor on the profit-taking sell quantity — applied before rounding/FIFO below:** `Quantity_Held * profit_sell_percentage / 100` is the normal sell target for GET THE PROFITS. If that slice, valued at `Current_Price`, is worth less than `min_value_of_trade`, compute a bump target = `min_value_of_trade / Current_Price`, rounded **UP to the 3rd decimal place** (not nearest — a plain 3-decimal round can round down and still fall short, e.g. `100 / 35 = 2.857142...` rounds to `2.857` = $99.995, still under $100; rounding up gives `2.858` = $100.03) — then run that 3-decimal figure through the same whole-share `round_sell_quantity` rounding the base `profit_sell_percentage` target already gets below (a specified-lot sell order requires a whole-share top-level quantity), capped at everything held, even past `profit_sell_percentage` (e.g. a 2-share/$70 slice at $35/share with `min_value_of_trade`=$100 and a 3rd share held: bump target `2.858` → `round_sell_quantity` → 3 whole shares = $105). This bump happens *before* the FIFO dollar-gate calculation below, so `Realized_Profit_Dollars` and the specified-lot selection are computed against the final, bumped quantity, not the original slice. If selling every whole share held still falls short of `min_value_of_trade`, skip the sale entirely this cycle (logged `SKIPPED`) rather than placing an order under the floor. This control does not apply to drawdown-stop liquidations (a full-position sale is placed regardless of its dollar size).
* **Sub-whole-share position fallback — ordinary order instead of specified-lot:** if the asset's *entire* remaining position (not just the `profit_sell_percentage` slice) is itself less than 1 whole share (e.g. 0.5 shares left after an earlier fractional buy), a specified-lot (`tax_lots`) sell can never be placed for it — `place_equity_order` rejects any `tax_lots` order whose top-level quantity is fractional, and every possible sell size out of a sub-1-share position is fractional by definition, so whole-share rounding would floor it to 0 every cycle and permanently block GET THE PROFITS on that position. In this case, size the sale in raw fractional shares — `Quantity_Held * profit_sell_percentage / 100`, uncapped by whole-share rounding, still topped up toward `min_value_of_trade` the same way (capped at everything held; skip if still short even selling 100%) — and place it as an **ordinary order** (omit `tax_lots`), letting Robinhood's own default lot matching apply, since ordinary orders accept fractional quantities freely. The FIFO walk over the held lots still runs for the dollar gate (`materialize_profit_in_dollars`), but since those lots aren't shipped to the order in this case, treat its `Realized_Profit_Dollars` figure as an estimate rather than a guarantee — note this explicitly in the journal reason for that sale.
* **Dollar-gate accounting for PARTIAL sales — use FIFO lot-matched cost basis, not `avg_cost_basis`:** `avg_cost_basis` is a whole-position blended average. Robinhood's actual realized gain on a sale that disposes of less than 100% of a position is computed lot-by-lot against whichever specific shares are disposed, and does not match the blended-average estimate whenever the position was built up at varying prices — confirmed empirically on 2026-07-29, where the blended-average estimate ($10,918.64 across 7 partial sales) undershot Robinhood's actual realized gain ($14,219.95, per `get_pnl_trade_history`) by $3,301.30. Before evaluating `materialize_profit_in_dollars` for any partial sale: call `get_equity_tax_lots` for the symbol; sort the returned lots by `open_date` ascending — true FIFO order; the tool's own default response order is newest-acquired-first, do not use it as-is; skip any lot with `is_selectable=false` or missing `cost_per_share`/`tax_cost_basis` (still syncing / pending — if this leaves insufficient priced+selectable quantity to cover the intended sale size, apply the same Fail-Closed treatment as the Step 1 `avg_cost_basis`-sourcing rule). **Round the sale target to a whole share before walking lots, not after:** confirmed empirically on 2026-08-04 — `place_equity_order` rejects any specified-lot (`tax_lots`) sell whose top-level order `quantity` is fractional (`"Order quantity cannot include fractional shares."`), even though the same account trades fractional shares freely on an ordinary (non-specified-lot) order, and even though `review_equity_order` does not simulate or catch the rejection. `Quantity_Held * profit_sell_percentage / 100` almost never lands on a whole-share boundary, so round that target to the nearest whole share first — capped at the whole shares actually held, floored at 0 (skip the sale entirely, logging `SKIPPED`, if the rounded quantity is 0) — and only then walk the sorted lots accumulating quantity until reaching that *rounded* target, taking only the needed partial amount from the lot where the cumulative crosses it. Rounding after computing `Realized_Profit_Dollars` instead of before would desync the dollar-gate figure from what actually gets ordered. Note this constrains only the order's *total* quantity to a whole number — the individual per-lot quantities inside `tax_lots` remain fractional wherever a lot's own fractional share balance requires it (they only need to sum to the whole total), so this does not force whole-share lots. `Realized_Profit_Dollars` (FIFO) = sum over every lot actually consumed of `(Current_Price − lot.cost_per_share) × quantity_taken_from_that_lot`. Gate `materialize_profit_in_dollars` against this FIFO figure, not the `avg_cost_basis` estimate. **When placing the sell order, pass this exact lot selection via `place_equity_order`'s `tax_lots` parameter** (do not leave it to Robinhood's default matching, which is not guaranteed to be date-ordered FIFO) so the dollar amount actually realized matches what was gated on. The percentage gate (`materialize_profit_percentage`) is unaffected by this — it describes overall position profitability and continues to use `avg_cost_basis`. For a full liquidation (drawdown stop-loss, 100% of the position), FIFO vs. average cost is moot — both yield the identical total realized gain — so no lot selection is required there. **v2.66.0 — mandatory positive-FIFO check:** because `avg_cost_basis` is a blended average and FIFO always disposes of the OLDEST lots first, a position built at DECREASING cost over time (expensive shares bought first, cheaper ones bought later) can show a positive `raw_gain_pct` against the blended average while the specific FIFO-matched lots being sold realize an actual dollar loss. The percentage gate (`materialize_profit_percentage`) is evaluated against `avg_cost_basis` and can pass in this scenario even though the sale itself would lose money — so, on top of whichever gate (percentage or dollar) actually passed, GET THE PROFITS additionally requires `fifo.fully_covered` **and** `Realized_Profit_Dollars > 0` unconditionally before firing; if the FIFO-matched dollars are zero or negative, the sale is skipped (logged `SKIPPED`) regardless of what the blended-average percentage gate said. This is what makes GET THE PROFITS structurally profit-gated in fact, not just on paper — the reason no wash-sale backward sell-guard is needed anywhere anymore. A defensive backstop still arms the `lastLossSaleDate`/`lastLossSalePrice` tracking if a sale with non-positive `Realized_Profit_Dollars` were ever placed despite this guard (e.g. a future change loosening it).
* **Loss-lot sell guard (v2.75.0) — never dispose of an underwater lot just because FIFO reached it:** A partial sale walks lots in FIFO (oldest-first) order, so a position built up at RISING cost hands the oldest — and cheapest — lots to the order first, while a position built at FALLING cost can hand over lots that are underwater at today's price even though the sale as a whole still clears its gates. Whenever the lots for a sale are being selected, **exclude every lot that would not realize a strict gain at `current_price`** (`cost_per_share >= current_price` — loss lots plus exact-breakeven lots, which consume sale quantity while contributing $0), and proceed with the remaining profitable lots. Concretely: cap the sale quantity at the total quantity of profitable lots (then re-apply the same whole-share flooring a specified-lot order requires — floor, never round up, since rounding up could re-admit an excluded lot), and walk only those lots for `Realized_Profit_Dollars`. **Ordering against the two neighbouring rules is load-bearing:**
  1. **The Fail-Closed pending-basis check runs FIRST and is unaffected.** If the sale target exceeds the total *priced + selectable* quantity, some shares' cost basis is still syncing/pending — that remains a hard skip per the Step 1 `avg_cost_basis` rule, and must NOT be quietly downsized into "sell only the lots that happen to be priced." The loss-lot cap applies only once basis is fully available.
  2. **The `min_value_of_trade` floor is re-checked AFTER the cap.** The cap can only shrink a sale, so a sale that cleared the floor before exclusion may fall under it afterwards; if it does, skip it entirely (logged `SKIPPED`, naming how much was held back) rather than placing an under-sized order.
  If *every* sellable lot is at or above the current price, there is nothing to sell at a gain — skip the sale entirely (logged `SKIPPED`). When the guard fires but the sale still proceeds, the journal reason records how many shares were held back and why, so a downsized sale is auditable. This makes the v2.66.0 positive-FIFO requirement structurally redundant (every consumed lot is now individually profitable, so the total cannot be ≤ 0) — that check is deliberately retained as a backstop. **Caveat on the sub-whole-share fallback:** when the whole position is under one share the order is placed as an ORDINARY (non-specified-lot) order, so the lot selection is not shipped to the broker and Robinhood's own default matching decides which shares are actually disposed. There the guard still caps the quantity and still governs the gating figure, but it cannot *guarantee* an underwater lot goes untouched — the same estimate-not-guarantee caveat that already applies to that path's `Realized_Profit_Dollars`.
* **GET THE PROFITS (portfolio-wide):** Sweep **every currently-held target asset** (any symbol in `portfolio_targets.json` with a nonzero position), **excluding any symbol in the `blocked` list** (Step 2) — a blocked asset is exempt from this sweep too; its `forceSell`+held liquidation, if applicable, is handled as its own dedicated full liquidation, not through GET THE PROFITS. For each remaining asset, compute both: its raw unrealized gain — `((Current_Price - Average_Cost_Basis) / Average_Cost_Basis) * 100` — against `materialize_profit_percentage`, and `Realized_Profit_Dollars` per the FIFO lot-matched dollar-gate rule above (the actual dollar profit that particular sale would lock in) against `materialize_profit_in_dollars`. **v2.63.0: fire the sale once EITHER gate clears its own bar — `materialize_profit_percentage` and `materialize_profit_in_dollars` are evaluated with OR, not AND; clearing just one is enough**, so both figures must be computed for every candidate regardless of which (if either) already passed. If neither gate clears, skip the sale this cycle (the position stays fully held and is re-evaluated fresh next cycle — no state is recorded for a non-fire). **Resell-cooldown guard:** even when a gate passes, check that symbol's `profitSellDate` in `peak/prices.json` — if `(current_date - profitSellDate) < profit_resell_cooldown_days`, skip the sale this cycle anyway (exempted until the cooldown window elapses; **v2.69.0: strict `<`, a gap exactly equal to the cooldown now clears it**; **v2.65.0: purely a flat calendar-day check, the prior Z-score recovery leg has been removed**). **v2.70.0/2.72.0 — `selling_price_change` guard:** independently of the cooldown, also require `(close_yesterday - current_price) * 100 / current_price < selling_price_change` (see `selling_price_change` above for the exact basis) before the sale is allowed to fire — skip it this cycle otherwise, even when every other gate has cleared. Missing/insufficient price history fails closed (skip). **`target_price_to_sell` guard:** independently of every gate above, also require `current_price` to have crossed the symbol's configured floor if one is set (see `target_price_to_sell` above) — skip the sale this cycle otherwise, even when every other gate/guard has cleared; this is the strongest of GET THE PROFITS' guards, since (unlike the others) it also overrides the emergency stop-losses elsewhere in this document. When a gate passes and no guard blocks it, sell `profit_sell_percentage` percent of that asset's position to realize the profit. This OVERRIDES `lock_in_period` for that asset and fires regardless of whether the asset is Underweight, Overweight, or within tolerance — for an Underweight asset this replaces its normal buy-to-cover-drift action for the cycle. Do not re-trigger this sale for a symbol if `peak/prices.json`'s `profitSellDate` for that symbol already equals `current_date` (i.e., it already had a GET THE PROFITS sale earlier today). Per the standing same-asset buy/sell exclusivity rule (Step 6), do not buy new shares of any asset that triggers a GET THE PROFITS sale this cycle. Beyond this cycle, the fresh `profitSellDate`/`profitSellPrice` this sale writes also arms the Step 2 `sold_asset_repurchase_days`/buy-timing buy-guard, which covers partial sales too — so the symbol stays blocked from new buys on subsequent cycles as well, until that guard clears.
* **Realized gains logging:** `Total_High_Beta_Gains_Realized` for the cycle = the sum of every executed GET THE PROFITS sale's FIFO lot-matched `Realized_Profit_Dollars`. (The retired Overweight-trim Beta ranking no longer exists; the metric name is retained for journal continuity.)

### 5. Price Limit & Volatility Halts
* **sell_price_diff_limit Rule:** If an asset's current price compared to its previous `no_of_days_for_price_compare` days max price drops by more than `sell_price_diff_limit` percent, exempt the asset from routine drift-selling on that day to avoid panic-selling an overextended dip. **Currently inert (v2.74.0):** routine drift-selling (Overweight trims) no longer exists, and GET THE PROFITS was always exempt from this rule — retained unchanged in case trims are ever reinstated.
* **buy_price_diff_limit Rule:** If a asset's current price compared to its previous `no_of_days_for_price_compare` days min price rallies up by more than `buy_price_diff_limit` percent, exempt the asset from buying on that day to prevent chasing parabolic moves.
* **52_week_high_guard Rule:** Applied against the same final buy dict as `buy_price_diff_limit`. If `current_price / fifty_two_week_high * 100 > 52_week_high_guard`, exempt the asset from buying entirely this cycle — by any means — to avoid chasing a symbol already trading near its 52-week high. Missing 52-week-high data (broker returns none) fails OPEN — the guard does not block, matching this Step's existing posture for missing historical bars.

### 6. Execute Sequential Trades
* Do not place any trade orders (either sell or buy) worth less than $`sell_or_buy_value_limit`
* **`min_value_of_trade` buy-side floor, applied to the final post-scaling buy amounts (after the hard-cap scaling below, before `sell_or_buy_value_limit`):** every planned buy should be worth at least `min_value_of_trade`. A buy under the floor is bumped up to it by taking dollars from lower-priority planned buys — buys rank by their own planned dollar amount, descending (a bigger amount reflects a bigger drift gap, i.e. more urgent). Dollars are drawn from the bottom of that ranking first, cascading as needed (a buy drained below its own floor gets its own turn to borrow from whatever's left further down). A buy that still can't clear the floor once every lower-ranked buy is exhausted is dropped (logged `SKIPPED`) rather than placed under-sized — its dollars simply stay wherever they were already redirected to; nothing is force-deployed beyond what's needed to clear floors.
* At any time you should not get into situation of buying and selling the same asset in the same cycle. if sale is for profit, execute the sales and ignore the buys otherwise ignore both. 
* Execute all necessary sell and liquidation orders (GET THE PROFITS sales and emergency liquidations) first to generate immediate buying power.
* **After all of this cycle's sells are confirmed and before sizing any buy:** re-call `get_realized_pnl` (same YTD window as Step 1) to finalize `net_realized_gains_ytd_effective` and `tax_reserve` per the Step 1 rule, then finalize the hard buy-spend cap below using that number. Buy sizing must use these final figures, not the Step 3 placeholder.
* Execute necessary buy orders on the momentum-ranked Underweight targets.
* Ensure at no point during execution does the live cash balance drop below `min_cash_absolute`.
* place orders sequentially rather than in parallel batches, to avoid throttling error from Robinhood MCP
* if Robinhood MCP returns "429 Request was throttled" on order placement, wait for 1 min and continue by retrying (retry max 3 times for each order) from the failed order and remaining orders. 
* **Extended Hours Execution:** Trading is permitted during active market hours and Robinhood extended hours (7:00–9:30 AM ET and 4:00–8:00 PM ET). Only route orders during extended hours for targeted assets that qualify for fractional share routing during those time windows other targeted assets makr them as SKIPPED/PENDING in the journal.

If peakPrice is null then update the file with current price and date, otherwise update peak price only if current price is greater than what is already there in file.  Reset the peakPrice if asset is repurchased after a profit-sell with purchase price. **Clear `liquidatedPrice` back to `""` and `liquidatedDate` back to `null`** whenever a buy fires this cycle for a symbol that previously carried a `liquidatedPrice` — i.e., the Step 2 recovery/cooldown gate passed and the asset is being repurchased. Leaving the old values in place would otherwise keep gating the position against a liquidation event that's no longer relevant now that it's held again.
