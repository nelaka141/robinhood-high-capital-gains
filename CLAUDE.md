## Hard Rules & Constraints
* **Scope Limit:** You are ONLY authorized to manage the specific high-beta equities and leveraged ETFs specified in the active `portfolio_targets.json` file. You may NEVER trade traditional options contracts, standalone cryptocurrencies, or futures.
* **Order Type:** Every trade execution MUST use standard Market Orders during active market hours to ensure instantaneous execution. During extended hours, you MUST use tight Limit Orders pegged directly to the last known Ask (for buys) or Bid (for sells). Never utilize margin or short selling.
* **Aggressive Execution:** Unlike static rebalancers, your purpose is to aggressively exploit volatility. You are authorized to clear out lagging positions entirely if they breach risk parameters to instantly fuel top-performing momentum vectors.
* **Error Handling:** If the Robinhood MCP server returns an API error or an unrecognized network state, immediately abort the routine, write a priority error log to `logs/trade_journal.md`, and terminate. retry 3 times (waiting 1 min between attempts) for "429 throttling" and "502 Bad Gateway" errors, other than this no retry loop.
* **Never force-push `main`, ever.** All changes to `main` — every cycle's trade journal/state-file commits, every code or `CLAUDE.md` change — go through a feature branch, a pull request, and a normal merge (`git push`, never `git push --force`/`--force-with-lease` to `main`). `main`'s history is the unalterable paper trail this whole bot exists to preserve; rewriting it defeats that purpose regardless of the reason. If `main` is ever genuinely broken and a revert is needed, open a revert PR and merge it forward — never reset/force-push the branch.

## Core Parameters & Risk Triggers
* `global_drift_tolerance`: Tight variance tolerance, expressed in **weight units** (the same scale as an asset's `weight`) — the allowed gap between an asset's set weight and its actual weight, kept tight to force frequent adjustments into winning positions. This is the **global default** — used for any asset that doesn't specify its own `drift` override in `portfolio_targets.json`.
* `max_trailing_drawdown_percentage`: Ultra-tight hard stop-loss: limits on current price drops with respect to max price and average cost basis of the asset.
* `min_recovery_price_percentage`: Taking risk again: if any asset's previously liquidated and now its price increased (compared to liquidated price) by >= min_recovery_price_percentage then this asset will come into play, as long this criteria does not meet this asset should be ignored from the drift calculations.
* `cool_down_period_after_lquidation`: days past after the previous lquidation
* `reinvestment_multiplier_factor`: Multiplier applied to deployable cash when fueling the primary momentum leader.
* `max_portfolio_percentage`:  cap on assets percentage of the total portfolio
* `alpha_cash_allocation_percentage`:  percent allocation of the deployable cash to aplha stock
* `min_cash_absolute`: The absolute bottom dollar floor that must NEVER be spent under any circumstances.
* `min_cash_target`: The lean cash buffer target designed to keep maximum capital deployed in risk assets.
* `seek_approval_value`: Trade size threshold in dollars above which you must halt and wait for user confirmation.
* `sell_price_diff_limit`: Percent single-day crash limit; skip selling if a asset collapses past this point to avoid selling at an absolute intra-day bottom.
* `buy_price_diff_limit`: Percent single-day pump limit; skip buying if an asset gaps up past this point to avoid chasing a blow-off top.
* `no_of_days_for_price_compare`: number of historic days to get min and max price of an asset for testing `buy_price_diff_limit` and `sell_price_diff_limit` limits
* `cap_on_total_cash_balance_to_use`: Maximum cash balance allowed for this strategy framework's **active deployable pool**, applied on top of (in addition to) `settlement_reserve_target` — i.e. it caps cash *after* the settlement reserve is set aside, not before. This can be greater than the current cash available in the account.
* `beta_benchmark_symbol`: The benchmark ticker (e.g., `SPY`) that all target assets' beta is measured against.
* `beta_calculation_lookback_days`: Trailing window of daily closes (e.g., 30) used to compute each asset's beta relative to `beta_benchmark_symbol`.
* `sold_asset_repurchase_days`: days past after asset sold for profit
* `sold_asset_price_change_percentage`: sold asset price drop percentage compared to price at previous sell.  previous sell price and sell data is in peak/prices.json
* `lock_in_period`: do not sell the assets if they are bought within `lock_in_period` days.  last purchase date (lastPurchaseDate) pull from peak/prices.json
* `overweight_sell_minimum_profit_margin_percent`:  do not sell the overweight assets if profit margin is not acheived ((market value - average cost basis ) / average cost basis ) * 100 >= overweight_sell_minimum_profit_margin_percent
* `momentum_reversal_minimum_profit_margin_percent`: minimum profit margin required before a Momentum Reversal Trim (downward-momentum sell, see Step 4) is allowed to fire — ((`current_price` - `avg_cost_basis`) / `avg_cost_basis`) * 100 >= `momentum_reversal_minimum_profit_margin_percent`. Dedicated and independently tunable from `overweight_sell_minimum_profit_margin_percent`, which only gates routine Overweight trims.
* `momentum_reversal_minimum_profit_dollars`: Minimum realized dollar profit a Momentum Reversal Trim must actually lock in — computed as `(Current_Price - Average_Cost_Basis) * (Quantity_Held * profit_sell_percentage / 100)`, the same formula as `materialize_profit_in_dollars` uses for GET THE PROFITS. This is an additional gate alongside `momentum_reversal_minimum_profit_margin_percent`, not a replacement: both the percentage gate and this dollar gate must pass for the trim to fire. Prevents firing on a position whose percentage gain and downtrend both qualify but whose position is small enough that the actual dollar profit realized wouldn't be worth the trade. Dedicated and independently tunable from `materialize_profit_in_dollars`, which only gates GET THE PROFITS sales.
* `profit_resell_cooldown_days`: Shared guard for GET THE PROFITS and Momentum Reversal Trim, checked against that symbol's `profitSellDate`/`profitSellPrice` in `peak/prices.json`: if `(current_date - profitSellDate) <= profit_resell_cooldown_days` **and** `current_price < profitSellPrice`, the symbol is exempted from firing *either* mechanism this cycle — even when the percentage gate and dollar gate both otherwise pass. Prevents locking in a smaller profit than the last trim already captured, or selling again into a price that hasn't recovered back above the last exit. A fresh profit-sell from either mechanism updates `profitSellDate`/`profitSellPrice` and re-arms this cooldown for both. **Does not apply the first time a symbol is ever profit-sold** — if `profitSellDate` is null/absent for that symbol (no prior GET THE PROFITS or Momentum Reversal Trim on record), there is nothing to compare against, so this guard never blocks a first-time fire; only a symbol with an existing `profitSellDate` within the cooldown window is subject to it. Distinct from `sold_asset_repurchase_days`, which gates *buying/repurchasing* a symbol after **any** profit-taking sale, partial or full (see Step 2) — this gates *re-selling* after any profit-taking sale, partial or full.
* `sell_or_buy_value_limit`:  lower limit on the sales or purchases or stock in dollars, this will prevent small dollars orders
* `min_value_of_trade`: A second, stricter dollar floor (checked after `sell_or_buy_value_limit`) that every surviving buy or sell should clear — but unlike `sell_or_buy_value_limit`'s blunt drop, a trade under this floor is first **bumped up to it** where the extra size can come from with no other side effect, and only dropped entirely if it genuinely can't reach the floor. **Buys:** a planned buy whose dollar amount is under `min_value_of_trade` is topped up by taking dollars from lower-priority planned buys (the Alpha Leader's buy is always highest priority; the rest rank by their own planned dollar amount, descending — a bigger amount reflects a bigger drift gap, i.e. more urgent). Lower-priority buys are drained from the bottom of that ranking first and can cascade — a buy drained below its own floor gets its own turn to borrow from whatever's left further down — and a buy that still can't clear the floor once every lower-ranked buy is exhausted is dropped rather than placed under-sized (logged SKIPPED). **Sells (GET THE PROFITS / Momentum Reversal Trim only):** if the `profit_sell_percentage` slice of a position is worth less than `min_value_of_trade`, sell additional whole shares from that same position — up to everything held — to clear the floor, even past `profit_sell_percentage`. If selling every whole share held still falls short of the floor, the sale is skipped entirely (logged SKIPPED) rather than placed under-sized. This does not apply to Overweight High-Beta trims (see Step 4) or to drawdown-stop liquidations, which are unconditional full-position sells.
* `settlement_reserve_target`: Fixed-dollar backup cash buffer (set in `portfolio_targets.json`), permanently walled off from `buying_power` before computing deployable cash. Used only to bridge buys whose funding sale hasn't settled yet; replenished automatically once the underlying sale is confirmed settled.
* `settlement_lag_days`: Expected settlement delay (e.g., 2 for T+2), used to set `expectedSettleDate` currently this is used only for recording.
* `materialize_profit_percentage` : realize the profit for any held asset whose unrealized gain exceeds this percentage — applies portfolio-wide to every currently-held target asset, not just the Alpha Leader.
* `profit_sell_percentage`:  only sell this much percentage of shares, in case of profit margin above `materialize_profit_percentage`. The resulting share count is rounded to the nearest whole share before it is used anywhere (lot selection, dollar gates, or the order itself) — see Step 4's "Dollar-gate accounting for PARTIAL sales" for why.
* `materialize_profit_in_dollars`: Minimum realized dollar profit a GET THE PROFITS sale must actually lock in — computed as `(Current_Price - Average_Cost_Basis) * (Quantity_Held * profit_sell_percentage / 100)`. This is an additional gate alongside `materialize_profit_percentage`, not a replacement: both must be satisfied for the sale to fire. Prevents firing on a position whose percentage gain clears the bar but whose position is small enough that the actual dollar profit realized wouldn't be worth the trade.
* `keep_aside_profits_for_tax_percent`: Percentage of year-to-date net realized equity gains (only when YTD is net-positive — nothing is set aside against a YTD loss) to wall off from deployable trading cash as a standing tax reserve, for trading purposes. This is a separate, dynamically-sized wall subtracted from `account_cash` alongside `min_cash_absolute` and `settlement_reserve_target` — see `tax_reserve` in Step 1 and Step 3.
* `momentum_lookback_days`: Number of trading days used to measure short-term technical momentum via RSI(14) and EMA(9) — specifically the window for the EMA(9) slope calculation in the `Momentum_Score` (see Step 3). Replaces the prior 7-day price % gain window as the basis for Alpha Leader selection.
* `momentum_reversal_threshold`: `Momentum_Score` threshold (see Step 4) at or below which a held, in-profit asset is flagged for a Momentum Reversal Trim — a short-term downtrend confirmed enough to lock in gains proactively, independent of `materialize_profit_percentage` / `materialize_profit_in_dollars`.

## Business Rules Reference (implemented in `bot/` — see "Execution Mode" above; do not execute this section yourself)
The sections below are the authoritative specification `bot/`'s Steps 1-6 (`bot/steps.py`) must implement exactly. They are not instructions for you to carry out by reasoning through them live — that's what the old (pre-v2.42.0) operating mode did, and why this section still exists is so that (a) you can consult it when the user asks you to change a rule, in which case update both this section AND the corresponding code in `bot/` in the same change, and (b) it documents *why* the script does what it does, for auditing a cycle's output against intent. ### 1. Fetch State & Track Trailing Drawdowns
* Read current portfolio balances, cash balance (`account_cash`), ticker equity values (`equity_value`), asset current price (`current_price`), assets average cost basis (`avg_cost_basis`) and asset price histories via the Robinhood MCP.
* **`avg_cost_basis` sourcing (primary → tax-lots → override, with reconciliation):** Resolve each held asset's `avg_cost_basis` as the average cost of the **entire position** (every share held, not a subset), in this order:
  1. **Primary — `get_equity_positions.average_buy_price`.** If populated, use it (it already reflects the full position).
  2. **Tax-lots, only when primary is null/empty — reconcile coverage first.** Call `get_equity_tax_lots` for the symbol, sum the `quantity` of lots that carry a basis (`cost_per_share`/`tax_cost_basis` present), and compare that covered quantity to the position `quantity`:
     * **Covered quantity ≈ position quantity** (within a small rounding tolerance): compute and use the share-weighted average — `avg_cost_basis = Σ(lot_quantity × lot_cost_per_share) / Σ(lot_quantity)`.
     * **Shortfall** (covered quantity < position quantity — some shares have pending/absent basis, e.g. **shares journaled/ACATS-transferred in from another account whose cost basis hasn't posted yet**): do NOT compute a partial average or treat it as the position average — the tax lots cover only the resident shares, not the transferred ones. Go to step 3.
  3. **Transferred-basis override — `transferred_basis.json` (repo root).** It maps `{ "SYMBOL": { "quantity": <shares>, "cost_per_share": <usd> }, ... }` — user-supplied cost of transferred-in shares whose basis Robinhood hasn't reconciled. If an entry exists for the shortfall symbol, compute the true blended average across the known-basis lots AND the override lot — `avg_cost_basis = (Σ(lot_quantity × lot_cost_per_share) + override_quantity × override_cost_per_share) / (Σ(lot_quantity) + override_quantity)` — and only use it if the combined quantity reconciles to the position quantity (within a small rounding tolerance).
  4. **Fail closed** — if the position's basis still can't be fully reconciled (primary null, tax-lots short, no matching `transferred_basis.json` entry, or the override still doesn't reconcile): treat every cost-basis-dependent gate for that asset — the Drawdown Audit cost-basis leg, `overweight_sell_minimum_profit_margin_percent`, GET THE PROFITS, Momentum Reversal Trim, and the High-Beta Raw-Gain score — as **NOT satisfied** this cycle (never sell on a partial or guessed basis), and log the asset as `SKIPPED (cost basis pending transfer)`. Drift/Overweight/Underweight sizing uses market value only and is unaffected — it still applies.
* `current_date` is the current calendar date in US ET timezone.
* Read the allocation targets from `portfolio_targets.json`. Each entry in `targets` is an object with a required `weight` and an optional `drift` (per-asset drift tolerance override, in weight units — same scale as `weight`). To calculate the target percent - `target_percentage` = (`weight` / sum_of_all_weights) * 100.
* **Per-asset drift resolution:** `asset_drift_tolerance` for an asset = its own `drift` field if present, otherwise the global `global_drift_tolerance`. Both are in **weight units**, and this resolved value is what "drift breach" is measured against everywhere below (the Drawdown Audit is unaffected — it uses `max_trailing_drawdown_percentage`, not drift). A never-held asset (no `peak/prices.json` entry) has `actual_weight` = 0, so its Drift equals its full set `weight`; it is treated with the same resolved tolerance as any other asset — there is no separate first-time-trade tolerance.
* `current_cash` = Math.min(`account_cash`, `cap_on_total_cash_balance_to_use` + `settlement_reserve_target`) — the cap applies to cash after the settlement reserve is reserved, so it does not eat into the reserve's own headroom.
* Account balance (`account_balance`) should be calculated as market value of all listed assets in `portfolio_targets.json` + `current_cash`
* Read `peakPrice`, `peakDate`, `liquidatedPrice`, `liquidatedDate`, `profitSellPrice`, `profitSellDate`, `lastPurchaseDate` from peak/prices.json file, if entry is null or not present assume current price is the peak.
* **Drawdown Audit Phase:** Before evaluating drift, check if any active asset has dropped ≥ `max_trailing_drawdown_percentage` from its `peakPrice` and also has dropped >= `max_trailing_drawdown_percentage` than the `avg_cost_basis`  (both the conditions need to match). In this case `lock_in_period` condition set in step 2. should be ignored.  If triggered, flag that asset for an emergency liquidation order down to 0%, overriding target weights.
* calculate Current percentage (`current_percentage`) of the asset based `account_balance`, and its actual weight: `actual_weight` = (`current_percentage` / 100) * sum_of_all_weights.
* Compute current drift for each asset **in weight units**: Drift = Math.abs(`weight` − `actual_weight`). This is the gap between the asset's set weight and its actual weight, compared directly against `asset_drift_tolerance` (also in weight units).
* Identify "Underweight" momentum assets (`target_percentage` > `current_percentage`) and "Overweight" assets (`current_percentage` > `target_percentage`).
* If no assets exceed their resolved `asset_drift_tolerance` and no drawdowns are breached, log a performance status summary to `logs/trade_journal.md` and terminate safely.  
* Read `settlement/reserve.json`. For each entry in `pending_draws`, check settlement: empirically confirm via `buying_power` now reflecting the sale (cash - buying_power ≈ 0 for that lot). Mark settled entries `settled: true` and remove them from `pending_draws` — this "returns" the advanced capital, replenishing the reserve.
* `reserve_available_to_draw` = `settlement_reserve_target` − sum(`reserveDrawn` across still-pending entries), floored at 0.
* Clarify `account_cash`/`current_cash` = the account's `buying_power` field (settled, spendable), not the raw `cash` ledger balance — `cash` can include unsettled proceeds that aren't actually usable, as discovered this cycle.
* **Tax reserve — multi-year carryover via `tax/realized_gains_by_year.json`, pre-trade snapshot, then a direct post-trade re-query (do not hand-reconstruct it):** Fetch year-to-date net realized equity gains via `get_realized_pnl` (`asset_classes: ["equity"]`, `start_date` = January 1 of the current year, `end_date` = `current_date`, scoped to this account) → `net_realized_gains_ytd_pretrade` = `total_returns` from that call. This necessarily excludes any GET THE PROFITS / Momentum Reversal Trim / Overweight-trim / drawdown-stop sale this same cycle is about to place — `get_realized_pnl` cannot see fills that haven't happened yet. **`tax_reserve` cannot be finalized until Step 6 has actually executed this cycle's sells.** Once Step 6 has placed and confirmed all of this cycle's sell/liquidation orders, **re-call `get_realized_pnl` with the identical YTD window** (same `start_date`/`end_date` = `current_date`) — confirmed empirically to reflect same-session fills immediately, no settlement wait needed — and take its fresh `total_returns` directly as `net_realized_gains_ytd_effective`. Do NOT compute this by summing `Realized_Profit_Dollars`/`High_Beta_Gain_Dollars` estimates onto the pretrade figure — those are `avg_cost_basis`-based approximations of the *gate* decision, not the actual lot-matched realized gain Robinhood records, and will systematically understate it (see the FIFO note in Step 4). **Multi-year carryover exists because `get_realized_pnl`'s YTD window resets to $0 every January 1st, but a prior year's tax liability doesn't disappear with the calendar** — `tax/realized_gains_by_year.json` is a stateful file keyed by calendar year (e.g. `{"2025": 8500.00, "2026": 13731.87}`). Every cycle, once `net_realized_gains_ytd_effective` is known, write/overwrite **only the current year's** entry with `Math.max(0, net_realized_gains_ytd_effective)` — do this every cycle regardless of whether any trades fired, and never touch any other year's entry. Because the write target is always keyed off `current_date`'s calendar year, the moment the year rolls over the write target itself becomes the new year's key, automatically freezing the just-ended year's entry at whatever it last recorded — no explicit year-end/rollover detection logic is needed. `prior_years_tax_base` = sum of every entry in `tax/realized_gains_by_year.json` for a year strictly before the current year (the current year's own contribution comes live from the API, not from the file). `tax_reserve` = (`prior_years_tax_base` + Math.max(0, `net_realized_gains_ytd_effective`)) * `keep_aside_profits_for_tax_percent` / 100. **This effective `tax_reserve` is what Step 3's `base_deployable_cash` and Step 6's reserve-bridge cap must both use** — since it is only known after Step 6's sells execute, treat any Step 3 multiplier/Alpha-allocation math computed earlier as a placeholder and re-run the buy-sizing once this final `tax_reserve` is in hand, before placing any buy order. **Manual clearing only:** a prior year's stored entry is reduced/zeroed only when the user directly edits `tax/realized_gains_by_year.json` (e.g. after actually withdrawing cash to pay that year's taxes) — the bot has no way to detect that a withdrawal was tax-motivated, so it never clears or decays a year's entry on its own. Log `net_realized_gains_ytd_pretrade`, `net_realized_gains_ytd_effective`, `prior_years_tax_base` (with each contributing year broken out), and the `tax_reserve` actually used.


### 2. Rules and Gaurd rails 
* Assets that are listed in `portfolio_targets.json` are only in scope for this bot, other asset having positions in the account should be ignored.
* Do not sell any assets within the `lock_in_period` (`current_date` - `lastPurchaseDate` <=  `lock_in_period` )
* Do not sell any overweight assets if the profit margin condition is not acheived,  "((`current_price` - `avg_cost_basis` ) / `avg_cost_basis` )  * 100 >= `overweight_sell_minimum_profit_margin_percent`" unless if asset is listed in `forceSell` list of `portfolio_targets.json`
* If any assets are lquidated previously (get the data from peak/prices.json) and (`current_price` - `liquidatedPrice`) is increased by more than `min_recovery_price_percentage` and (`current_date`- `liquidatedDate`) >= `cool_down_period_after_lquidation` then only you can repurchase the assets to cover drift and hence bring that asset into play again. **This gate only applies while the asset is currently unheld (quantity 0).** Once repurchased, `liquidatedPrice`/`liquidatedDate` are cleared back to `""`/`null` (see Step 6) so a past liquidation never re-gates a position you're actively holding again — a repurchase that clears the recovery/cooldown check is the only way `liquidatedPrice` gets cleared, so until that clearing happens, treat a stale entry as inert for any symbol with a nonzero position: check live holdings, not just the presence of these fields, before excluding a symbol from drift/Alpha-Leader play.
* If any assets are sold for profit previously (get the data from peak/prices.json) and (`current_price` - `profitSellPrice`) is dropped by more than `sold_asset_price_change_percentage` and (`current_date` - `profitSellDate`) >= `sold_asset_repurchase_days` then only you can buy/repurchase the asset to cover drift and bring it back into play for buying. **This buy-guard applies uniformly to every profit-sell recorded in `profitSellDate`/`profitSellPrice` — both a full-exit profit sale (100% of the position, quantity 0 after the sale) and a partial GET THE PROFITS trim or Momentum Reversal Trim (both Step 4, which sell only `profit_sell_percentage`% of the position).** In the full-exit case the asset holds a zero position and is entirely out of play until the guard clears (as before). ### 3. Calculate Alpha Leader & Apply Re-investment Multiplier
* **Alpha Leader selection — Momentum Score (replaces the prior 7-day price % gain rule):** For every target asset currently in play (respecting the Step 2 exclusions — liquidated/excluded assets stay out of the running until they clear recovery), pull at least 30 days of daily RSI(14) and EMA(9) via `get_equity_technical_indicators` (30 days for RSI stability, comfortably more than `momentum_lookback_days`) and compute.   * `RSI14` = the latest 14-period RSI value.
  * `EMA9_now` = the latest 9-period EMA value; `EMA9_prior` = the 9-period EMA value from `momentum_lookback_days` trading days earlier.
  * `Price_vs_EMA_Pct` = `(Current_Price - EMA9_now) / EMA9_now * 100` — is price trading above or below its own short-term trend line.
  * `EMA_Slope_Pct` = `(EMA9_now - EMA9_prior) / EMA9_prior * 100` — is that trend line itself rising or falling.
  * `Momentum_Score` = `Price_vs_EMA_Pct + EMA_Slope_Pct + (RSI14 - 50)`.
  The **Alpha Leader** is the in-play asset with the highest `Momentum_Score` — the higher the score, the stronger the confirmed short-term uptrend (price above a rising 9 EMA, RSI on the bullish side of neutral).

  * Calculate the multiplier injection: `multiplier_cash` = `base_deployable_cash` * (`reinvestment_multiplier_factor` - 1.0).
  * **Rule:** Allocate `alpha_cash_allocation_percentage`% of the `base_deployable_cash` PLUS the extra generated `multiplier_cash` (harvested by safely trimming the most overweight or lowest-momentum positions in step 1) directly into the Alpha Leader, up to a maximum cap of `max_portfolio_percentage`% total portfolio concentration for that single asset.
* Re-calculate portfolio percentages and remaining asset drift after routing the multiplier cash. If all assets are brought within the target boundaries, skip directly to Step 6.
* Divide the scarce capital on pro-rata basis among drifted assets for purchase to cover the drift

### 4. Evaluate Aggressive Profit-Taking & Reallocation
* **`min_value_of_trade` floor on the profit-taking sell quantity — applied before rounding/FIFO below:** `Quantity_Held * profit_sell_percentage / 100` is the normal sell target for GET THE PROFITS and Momentum Reversal Trim. If that slice, valued at `Current_Price`, is worth less than `min_value_of_trade`, sell additional whole shares from the same position — up to everything held — to clear the floor, even past `profit_sell_percentage` (e.g. a 2-share/$70 slice at $35/share with `min_value_of_trade`=$100 and a 3rd share held becomes a 3-share/$105 sale). This bump happens *before* `round_sell_quantity` and the FIFO dollar-gate calculation below, so `Realized_Profit_Dollars` and the specified-lot selection are computed against the final, bumped quantity, not the original slice. If selling every whole share held still falls short of `min_value_of_trade`, skip the sale entirely this cycle (logged `SKIPPED`) rather than placing an order under the floor. This control does not apply to Overweight High-Beta trims or to drawdown-stop liquidations (a full-position sale is placed regardless of its dollar size).
* **Dollar-gate accounting for PARTIAL sales — use FIFO lot-matched cost basis, not `avg_cost_basis`:** `avg_cost_basis` is a whole-position blended average. Robinhood's actual realized gain on a sale that disposes of less than 100% of a position (GET THE PROFITS, Momentum Reversal Trim, or a routine Overweight trim under 100%) is computed lot-by-lot against whichever specific shares are disposed, and does not match the blended-average estimate whenever the position was built up at varying prices — confirmed empirically on 2026-07-29, where the blended-average estimate ($10,918.64 across 7 partial sales) undershot Robinhood's actual realized gain ($14,219.95, per `get_pnl_trade_history`) by $3,301.30. Before evaluating `materialize_profit_in_dollars` / `momentum_reversal_minimum_profit_dollars` for any partial sale: call `get_equity_tax_lots` for the symbol; sort the returned lots by `open_date` ascending — true FIFO order; the tool's own default response order is newest-acquired-first, do not use it as-is; skip any lot with `is_selectable=false` or missing `cost_per_share`/`tax_cost_basis` (still syncing / pending — if this leaves insufficient priced+selectable quantity to cover the intended sale size, apply the same Fail-Closed treatment as the Step 1 `avg_cost_basis`-sourcing rule). **Round the sale target to a whole share before walking lots, not after:** confirmed empirically on 2026-08-04 — `place_equity_order` rejects any specified-lot (`tax_lots`) sell whose top-level order `quantity` is fractional (`"Order quantity cannot include fractional shares."`), even though the same account trades fractional shares freely on an ordinary (non-specified-lot) order, and even though `review_equity_order` does not simulate or catch the rejection. `Quantity_Held * profit_sell_percentage / 100` almost never lands on a whole-share boundary, so round that target to the nearest whole share first — capped at the whole shares actually held, floored at 0 (skip the sale entirely, logging `SKIPPED`, if the rounded quantity is 0) — and only then walk the sorted lots accumulating quantity until reaching that *rounded* target, taking only the needed partial amount from the lot where the cumulative crosses it. Rounding after computing `Realized_Profit_Dollars` instead of before would desync the dollar-gate figure from what actually gets ordered. Note this constrains only the order's *total* quantity to a whole number — the individual per-lot quantities inside `tax_lots` remain fractional wherever a lot's own fractional share balance requires it (they only need to sum to the whole total), so this does not force whole-share lots. `Realized_Profit_Dollars` (FIFO) = sum over every lot actually consumed of `(Current_Price − lot.cost_per_share) × quantity_taken_from_that_lot`. Gate `materialize_profit_in_dollars` / `momentum_reversal_minimum_profit_dollars` against this FIFO figure, not the `avg_cost_basis` estimate. **When placing the sell order, pass this exact lot selection via `place_equity_order`'s `tax_lots` parameter** (do not leave it to Robinhood's default matching, which is not guaranteed to be date-ordered FIFO) so the dollar amount actually realized matches what was gated on. The percentage gates (`materialize_profit_percentage`, `momentum_reversal_minimum_profit_margin_percent`, `overweight_sell_minimum_profit_margin_percent`) are unaffected by this — they describe overall position profitability and continue to use `avg_cost_basis`. For a full liquidation (drawdown stop-loss, 100% of the position), FIFO vs. average cost is moot — both yield the identical total realized gain — so no lot selection is required there.
* **GET THE PROFITS (portfolio-wide):** Before the routine Overweight-trim pass below, sweep **every currently-held target asset** (any symbol in `portfolio_targets.json` with a nonzero position — not just the Alpha Leader). For each, if its raw unrealized gain — `((Current_Price - Average_Cost_Basis) / Average_Cost_Basis) * 100` — exceeds `materialize_profit_percentage`, compute `Realized_Profit_Dollars` per the FIFO lot-matched dollar-gate rule above (the actual dollar profit that particular sale would lock in — NOT `(Current_Price - Average_Cost_Basis) * (Quantity_Held * profit_sell_percentage / 100)`, which understates it). **Only fire the sale if `Realized_Profit_Dollars` also exceeds `materialize_profit_in_dollars`** — both the percentage gate and the dollar gate must pass. If the percentage bar clears but the dollar amount doesn't, skip the sale this cycle (the position stays fully held and is re-evaluated fresh next cycle — no state is recorded for a non-fire). **Resell-cooldown guard:** even when both gates pass, check that symbol's `profitSellDate`/`profitSellPrice` in `peak/prices.json` — if `(current_date - profitSellDate) <= profit_resell_cooldown_days` AND `current_price < profitSellPrice`, skip the sale this cycle anyway (exempted until the cooldown window elapses or price recovers back above `profitSellPrice`); this guard is shared with Momentum Reversal Trim, see below. When all gates pass, sell `profit_sell_percentage` percent of that asset's position to realize the profit. This OVERRIDES `lock_in_period` for that asset and fires regardless of whether the asset is Underweight, Overweight, or within tolerance — for an Underweight asset this replaces its normal buy-to-cover-drift action for the cycle. Do not re-trigger this sale for a symbol if `peak/prices.json`'s `profitSellDate` for that symbol already equals `current_date` (i.e., it already had a GET THE PROFITS sale earlier today). Per the standing same-asset buy/sell exclusivity rule (Step 6), do not buy new shares of any asset that triggers a GET THE PROFITS sale this cycle. If the Alpha Leader itself triggers this rule, skip its Step 3 multiplier buy-allocation for this cycle and redirect that capital pro-rata among the remaining Underweight targets instead. Beyond this cycle, the fresh `profitSellDate`/`profitSellPrice` this sale writes also arms the Step 2 `sold_asset_repurchase_days`/`sold_asset_price_change_percentage` buy-guard, which now covers partial sales too — so the symbol stays blocked from new buys on subsequent cycles as well, until that guard clears.
* **MOMENTUM REVERSAL TRIM (portfolio-wide, downward short-term trend):** Using the same `Momentum_Score` computed in Step 3 for **every currently-held target asset** (not just Overweight ones, and independent of GET THE PROFITS), if an asset's `Momentum_Score` is at or below `momentum_reversal_threshold` — a confirmed short-term downtrend: price below its 9 EMA, that EMA itself falling, RSI below neutral — AND its raw unrealized gain clears `momentum_reversal_minimum_profit_margin_percent` (genuinely in profit, not just technically weak), compute `Realized_Profit_Dollars` per the FIFO lot-matched dollar-gate rule above (the actual dollar profit that particular sale would lock in — NOT the `avg_cost_basis`-based formula, which understates it). **Only fire the trim if `Realized_Profit_Dollars` also exceeds `momentum_reversal_minimum_profit_dollars`** — the percentage gate, the downtrend condition, and this dollar gate must all pass. If the score/percentage conditions clear but the dollar amount doesn't, skip the trim this cycle (the position stays fully held and is re-evaluated fresh next cycle — no state is recorded for a non-fire). **Resell-cooldown guard (shared with GET THE PROFITS):** even when all of the above pass, check that symbol's `profitSellDate`/`profitSellPrice` in `peak/prices.json` — if `(current_date - profitSellDate) <= profit_resell_cooldown_days` AND `current_price < profitSellPrice`, skip the trim this cycle anyway, exempted until the cooldown window elapses or price recovers back above `profitSellPrice`. When all gates pass, sell `profit_sell_percentage` percent of that asset's position to lock in gains ahead of the reversal. This OVERRIDES `lock_in_period`, same as GET THE PROFITS. Skip this rule for a symbol that already had a GET THE PROFITS sale (or a prior Momentum Reversal Trim) earlier the same day — check `peak/prices.json`'s `profitSellDate` for that symbol against `current_date`; this is one shared same-day guard covering both mechanisms, so a symbol never gets sold twice via profit-taking rules in one day. Per the standing buy/sell exclusivity rule (Step 6), do not buy new shares of any asset that triggers a Momentum Reversal Trim this cycle. Beyond this cycle, the fresh `profitSellDate`/`profitSellPrice` this trim writes also arms the Step 2 `sold_asset_repurchase_days`/`sold_asset_price_change_percentage` buy-guard (now covering partial sales too), so the symbol stays blocked from new buys on subsequent cycles as well, until that guard clears. Like GET THE PROFITS, these trims are mandatory once triggered — not part of the ranked Overweight High-Beta selection pool below — but score and log them with the same Beta/Raw-Gain/High-Beta-Score formulas and fold their dollar gain into `Total_High_Beta_Gains_Realized`.
* If drift still exceeds tolerance or extra cash is required to fulfill the Re-investment Multiplier engine from Step 2, identify (remaining — not already sold via GET THE PROFITS or Momentum Reversal Trim this cycle) Overweight assets to trim.
* **NO TAX LOCK:** There is no tax appreciation ceiling. You are actively encouraged to trim assets that have extended past their targets to lock in high-beta gains and fund the Alpha Leader.
* Calculate the required sell volume from Overweight or trailing-stop-breached assets to generate the exact buying power required to fulfill Underweight and Multiplier targets.
* **High-Beta Gains Calculation:** Before choosing which Overweight assets to trim, score and rank every Overweight candidate as follows:
  1. **Beta:** For each candidate, pull `beta_calculation_lookback_days` of daily closes for the asset and for `beta_benchmark_symbol` via `get_equity_historicals`, compute daily returns for both series, then:
     `Beta_asset = Covariance(Asset_Daily_Returns, Benchmark_Daily_Returns) / Variance(Benchmark_Daily_Returns)`
  2. **Raw unrealized gain:** Using `avg_cost_basis` resolved per Step 1 (the `get_equity_positions` field, else the `get_equity_tax_lots` share-weighted fallback):
     `Raw_Gain_Percentage = ((Current_Price - Average_Cost_Basis) / Average_Cost_Basis) * 100`
  3. **High-Beta Gain Score:** `High_Beta_Gain_Score = Raw_Gain_Percentage * Beta_asset`
     This weights a position's profit by the market risk taken to earn it, so a 20% gain on a 2.5-beta leveraged ETF (score 50) ranks above a 20% gain on a 1.0-beta asset (score 20) — same return, more risk retired.
  4. **Ranking:** Sort Overweight candidates by `High_Beta_Gain_Score` descending. Trim from the top of this ranking first when harvesting capital for Underweight targets or the Alpha Multiplier, so the most amplified/highest-conviction gains are the first ones locked in. **GET THE PROFITS and Momentum Reversal Trim sales are mandatory once triggered (like drawdown stop-losses) — they are not part of this ranked-selection pool, but score and log them with the same Beta/Raw-Gain/High-Beta-Score formulas.**
  5. **Realized dollar gain (for logging):** For a partial sale (GET THE PROFITS, Momentum Reversal Trim, or a routine Overweight trim under 100% of the position), `High_Beta_Gain_Dollars` = the FIFO lot-matched `Realized_Profit_Dollars` computed per the dollar-gate rule above — NOT `(current_price - avg_cost_basis) * Shares_Sold`, which understates it whenever the position was built up at varying prices. For a full liquidation (100% of the position, e.g. a drawdown stop-loss), `High_Beta_Gain_Dollars` = `(current_price - avg_cost_basis) * Shares_Sold` is exact (FIFO and average cost necessarily agree when every lot is disposed). Sum across all trims executed this cycle — including GET THE PROFITS and Momentum Reversal Trim sales — as `Total_High_Beta_Gains_Realized`.

### 5. Price Limit & Volatility Halts
